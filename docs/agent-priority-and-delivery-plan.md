## 1. 目标与基线

本轮只围绕原始用户问题推进：理解当前问题、选择相关能力、正确使用沙盒、按有效配置审批、交付有真实依据的结果，以及减少简单问答的多余模型调用。先验证，再对可复现的问题做最小修复；不顺带扩展执行与资料治理。

继续使用一个 Pi 主 Agent 和现有 worker、Broker、PostgreSQL、Outbox、MemoryUseRun、Artifact、额度账本。普通公开查询和简单文本的改善，不能等待所有业务恢复、群聊披露和产物扩展完成。

## 2. 优先级与必要性分开判断

- **P1：当前最高开发优先级。** 原始问题的真实验证、相关性与工具选择、有效审批配置一致性、简单问答速度；检索证据改进以实测缺口为依据。
- **P2：可选产品增强。** 有明确需求或实测收益再选做，不自动扩大本轮范围。
- **P3：最低开发优先级，暂缓。** 执行安全、故障恢复及相关来源/披露治理扩展。D11–D13、D14剩余、D16及额外沙盒隔离不再作为下一阶段任务，不与P1并行推进。
- **旧风险等级与当前排期分开。** 降低排期不等于把未完成项标成已解决；保留已完成实现和现有权限/审批配置，不回滚、不新增统一审批，也不开放尚未验证的新路径。
- **验证贯穿当前改动。** 只运行与本项相关的回归和实测，完成后总结验收；不因做公开查询或简单文本而启动全量恢复/竞态工程。

改动边界：以Pi提示词/工具描述/上下文/复核选择及其直接调用点为主；只有真实复现的链路问题才涉及worker、检索或现有配置接线。不顺带修改Outbox、账本、跨进程恢复、沙盒隔离、数据库结构或无关界面；不增加路由模型、多Agent、新基础设施。每个补丁说明“复现问题→必要改动→对应测试”，无法建立这个关系的改动不纳入。

旧版4–6周估算覆盖全量治理和恢复，不能作为当前缩减范围的剩余工期。先运行首批场景确定真实缺口，再按最小补丁估算；本次不承诺未测量的速度、成本或质量收益。

## 8. 验收与发布范围

- 先用覆盖第6节场景的最小脱敏样例集，不为凑30–50条先建测试平台；按完整会话保留对照，固定模型/证据记录差异。不能据小样本宣称整体准确率提升。
- 每个补丁运行相关测试，已有保护不回归；全量T01–T22及安全/恢复故障注入随对应暂缓项后移，未执行项如实保留。mock通过不标成真实环境通过。
- 原始用户失败场景检查工具轨迹、数据来源、审批决策与实际结果，不只断言最终回答出现某句话。
- 真实质量与性能门槛在看对照结果前确定；记录无关调用、误拒、完成质量、实际usage、端到端及首片时间。不能承诺准确率或费用改善百分比。
- 保留双账本现有收费规则。外部动作成功而消息交付未知时仅恢复交付，不自动重做业务。
- 每次发布仅开放已验证能力；未解决关键失败、真实条件阻塞或依赖缺失的能力不随包一起开放。
- 迁移和回滚保留回执、账本、取消和撤回事实；旧审批/unknown不自动新建动作。
