# 通用智能体执行链路：工程评估与修改建议

日期：2026-09-23。基线：`fix/knowledge-browser-import` / `2168618`，包含当前工作区已有修改。
状态：核心改动已实现并在本机验证（2026-09-24）。本文保留原设计目标；实际实现、验证和未覆盖边界见 [验证报告](../reports/agent-execution-loop/verification.md)。

## 结论

推荐保留现有 Pi 单一 Agent 循环，修正它的任务状态、工具反馈、审批恢复和完成判定。不同场景共用通用能力，业务内容进入任务目标和工具参数，不增加行业专用路由分支。

100 个问题可以有 100 条评测样例，不应需要 100 套工具选择代码。MCP 是接入协议，浏览器是执行方式，Web 是信息访问能力；这些名称本身不决定优先级。

### 方案比较

| 方案 | 结果 | 判断 |
| --- | --- | --- |
| 继续加关键词和行业工具路由 | 局部修复快，换一种说法或跨场景组合就容易漏掉 | 不采用 |
| 在现有 Pi 中建立通用目标、观察结果与恢复契约 | 复用现有基础设施，改造与故障发生的位置一致 | 推荐 |
| 重建独立 Planner/Executor/Reviewer 多 Agent 服务 | 状态、审批、预算和错误恢复需要跨更多服务协调 | 当前收益不足，不采用 |

完整改造跨越运行时、worker、审批持久化和浏览器适配，复杂度不能用“改一句提示词”掩盖。应分为有独立验收的增量改动；不一次重写整个系统，也不把关键恢复路径作为可选尾项。

## 当前通用缺陷

| 优先级 | 发现 | 影响 |
| --- | --- | --- |
| P0 | `runtime.ts` 在正常 Agent 结束后追加多个强制工具提示 | 可能把“回答原问题”变成“必须调用某类工具” |
| P0 | 新鲜度检查依赖调用次数和 `web/mcp` 来源类别 | 工具返回成功、甚至真实返回天气，都不能证明回答了用户的问题 |
| P0 | 审批恢复只保存 approvalId 和产物，并删除整个 sandbox adapter | 丢失步骤状态；无法正常继续下一次浏览，也难以处理多次审批 |
| P0 | worker 将 `!approvalRequired` 同时当作 `readOnly`、`idempotent` | 无需审批不等于无副作用或可安全重试 |
| P1 | 浏览器导航成功即记为执行成功，缺少明确的 HTTP/限流/内容可用性结果 | 429、登录页、空数据页可能被误认为已完成任务 |
| P1 | `PiWebAdapter` 有接口，但生产 `buildPiAdapters` 没有接入 `web` | 模型实际可用的公共信息通道与“Web 已支持”的预期不一致 |
| P1 | 显式工具限制依赖中文/英文关键词，并可能整轮屏蔽一类工具 | 无法稳妥处理同义表达及“先浏览，再调用外部服务”的组合任务 |
| P1 | 恢复时重新创建运行实例，步骤预算和诊断记录缺少完整的跨恢复语义 | 可能重复执行、重复审批或只看到后半段调用记录 |

主要定位：

- `packages/model-runtime/src/pi/runtime.ts`：工具裁剪、追加纠偏轮次、完成判定。
- `packages/model-runtime/src/pi/tools.ts`：能力描述、调用计数、结果收集、重试语义。
- `apps/conversation-worker/src/processor-pi.ts`：工具实际接线、审批后重建、MCP 属性来源。
- `packages/web-data/src/pi-approval-continuation.ts`：当前恢复数据结构。
- `packages/web-data/src/compute-conversation-results.ts`：审批结果回写与重新入队。
- `apps/compute-broker/src/browser.ts`、`executions.ts`：浏览器观察结果及持久化。

这些是流程缺陷。代表人设可以影响表达风格，但不能把用户目标换成与人设更接近的问题。

## 建议的通用执行循环

```text
用户请求 + 允许使用的资料与能力
             |
             v
任务目标 / 约束 / 完成条件 / 总预算
             |
             v
Pi 选择当前最有用的一步 <---------------------------+
             |                                    |
             v                                    |
权限、额度、方法约束、幂等与预算校验                  |
       |                 |                        |
    可执行            需要审批                      |
       |                 v                        |
       |          保存 checkpoint → 等待            |
       |                 |                        |
       |         验证回调与权限 → 恢复原步骤           |
       +-----------------+                        |
             |                                    |
             v                                    |
执行 → 结构化观察结果 → 对照原目标评估                |
                        |                         |
               +--------+---------+               |
               |                  |               |
            证据充分       不充分且还有可用方法 ------+
               |                  |
               v                  v
          有依据的最终回复   预算耗尽/不可恢复/缺用户信息
                                  |
                         明确的部分结果、失败或澄清
```

### 1. 固定目标，允许修改步骤

为需要工具的任务维护轻量 `TaskState`，不新增独立规划服务。任务目标来自当前用户请求和已授权上下文；工具返回内容只能更新观察结果，不能改写目标。

建议包含：`goalRef/goalVersion`、用户方法约束、需要交付的结果、完成条件、已有观察结果引用、当前步骤、待审批操作、剩余预算。

例如“查询某对象今天的情况”保存对象、时间范围和需要的信息，而不是登记一个“金融/天气/旅游”的行业枚举。换成产品参数、出行时间或文档分析，结构仍然相同。

不要求所有闲聊都额外调用规划模型。纯文本简单任务保持现有快路径；有工具需求时在现有模型轮次中形成结构化任务/步骤状态，必要时最多做一次解析修正。任务复杂度不应机械地增加模型调用层数。

阶段 A 应同时清理此前排错加入的行业提示和关键词工具裁剪，将用户的方法要求归入任务约束。仍保留权限、来源隔离和附件真实读取等通用硬约束。方法约束的语义抽取也需评测；无法确定时澄清，不能假定模型自报的目标必然完整。

### 2. 工具按能力描述，选择按任务适配

保持少量通用能力：

- 公共 Web 搜索：发现候选来源。
- 网页读取：获取可直接读取的页面内容。
- 沙盒浏览器：处理页面渲染、截图和受控交互。
- 沙盒代码与文件：执行计算、解析输入、验证并生成产物。
- 知识检索：访问当前授权范围内的资料。
- MCP：使用已发布、可说明输入输出和副作用的外部能力。

优先级不是固定的“Web > MCP > 浏览器”，而是：

1. 必须符合用户的方法约束、数据边界、能力权限和消费额度。
2. 能为当前缺失结果提供相关证据。
3. 满足时效性、交互及输出格式要求。
4. 在同等可用的方法之间，优先成本较低、延迟较小、可靠性更好的方法。

未知网址通常先搜索；已知可直接读取的网址通常先读取；需要脚本渲染或交互时使用浏览器；现有结构化工具确实匹配需求时可以直接使用。它们是通用操作特征，不是行业分支。

用户约束应绑定到其指定的目标或步骤。例如“用浏览器查资料，再通过 MCP 写入系统”不能因为前半句出现浏览器就屏蔽整轮 MCP。

语义适配仍需要模型判断，不存在靠几个布尔字段就保证选对工具的办法。后端强制确定性的权限和流程边界；统一的证据评估与跨场景评测负责约束语义偏离。不能把模型自报的“相关”“只读”作为安全授权。

### 3. 统一结果契约，分开执行与完成

建议在现有 `PiCapabilityResult` 上增量增加结构化观察信息，先兼容旧适配器：

| 信息 | 含义 |
| --- | --- |
| 操作状态 | 完成、失败、等待审批、结果未知 |
| 观察结果 | 内容/字段及受保护的结果引用；允许标记为空或被阻断 |
| 来源 | 实际 URL、服务、文件或业务记录坐标 |
| 时间 | 抓取时间与来源数据时间分别记录；不能相互替代 |
| 问题 | 超时、限流、登录阻断、缺字段、解析失败等通用原因 |
| 恢复属性 | 是否允许重试、是否需要查询远端最终状态 |

后端校验结构、状态码、产物完整性及明确的失败信号；Agent 对照原目标评估内容是否相关且充分。必要时对候选最终答复做一次有界语义核验，并给出缺失项，不能继续以“调用过工具”代替核验。

完成判定的对象是目标中的结果，不是工具类别。网页打开成功但没有目标内容，或 API 返回了不相关数据，都不能标记任务完成。网页、MCP、文件的有效证据使用同一种判定方式。

语义核验也是模型能力，存在误判和相关性偏差。它不是新的权限边界，也不能保证任意网站或任意任务必然成功；必须用保留测试集衡量效果，允许明确的部分成功或失败。

### 4. 审批是暂停原任务

扩展现有持久化结构为版本化 checkpoint，保留：

- 任务目标及目标版本；
- 原生 tool-call ID、步骤 ID、已完成操作及结果引用；
- 待审批操作、规范化参数摘要和授权范围；
- 剩余步骤/重试预算、截止时间、配置版本及租约 revision。

审批成功后，将真实结果对应回原 tool call，使用 Pi 的状态恢复和 `continue()` 继续原任务。只阻止同一个操作重复执行，不移除整个浏览器或沙盒能力。访问另一页、处理另一个文件仍是合法的新步骤，并单独遵守当前权限。

恢复必须复用现有数据库事务、工作租约、幂等和 fencing：旧审批回调不能覆盖新的待审批状态；重复回调不得重复执行或结算；取消、权限撤回和额度失效后不能恢复外部操作。

checkpoint 保存必要的模型可用上下文和受保护的结果引用，不把凭据、Cookie、大型原始结果或隐藏推理写入普通日志。恢复时重新验证数据来源授权，不能让缓存上下文绕过知识/记忆撤回。

### 5. 通用恢复策略保持原目标

| 情况 | 建议动作 |
| --- | --- |
| 只读请求的短暂超时/429 | 在同一步预算内有限重试，尊重 Retry-After；可换符合原目标的来源 |
| 页面需渲染、直接读取不完整 | 在用户允许时升级到浏览器 |
| 登录或权限阻断 | 明确需要何种授权；不绕过访问控制 |
| 返回空数据/错误对象 | 更新缺失项，换相关来源或方法，保留已取得的有效部分 |
| 写操作结果未知 | 先查询/对账；不能自动再写一次或换服务重复提交 |
| 用户必须补充信息 | 问最少且明确的问题 |
| 总预算耗尽 | 给出可验证的部分结果与未完成原因 |

不以换工具为目的重试，也不为了满足“必须有实时调用”而调用不相关服务。

### 6. 读写、审批与重试属性独立

将 `approvalRequired`、`effect`、`idempotency` 分开。优先复用 Broker 已有的服务端能力分类和 schema 指纹；外部 MCP 自报 annotations 只作提示，不能直接作为信任依据。

无依赖、无待审批且被确认安全的读取可并行。有依赖、可能产生写入或需要审批的步骤按顺序推进。Pi 的 `terminate` 是当前工具批次结束提示，不是已启动外部操作的回滚；不能只靠该提示实现审批屏障。

## 工程实施建议

| 阶段 | 主要改动 | 验收 |
| --- | --- | --- |
| A：统一循环与证据 | 在现有 runtime/types/tools 和 worker 中引入目标/观察结果契约；用 Pi 钩子取代重复追加的工具类别提示；拆开 MCP 属性 | 未明确点名工具的跨场景请求也不偏离；无关数据和阻断页面不算完成；普通问答不增加工具调用 |
| B：可靠暂停与恢复 | 版本化 `pi-approval-continuation`，协调 conversation-platform 与 compute-conversation-results 的原子状态；原 tool-call 结果回填后继续 | 跨进程恢复、多次审批、重复回调、取消、权限收紧、额度失效全部有测试；预算不重置 |
| C：通用 Web 与浏览器观察 | 将真正配置好的 Web provider 或通用搜索 MCP 接到 `PiWebAdapter`；补齐页面读取、浏览器状态和来源信息 | 搜索、读取、浏览器至少有一条真实可用链路；未配置的能力不暴露，限流/空内容如实反馈 |

A/B 是同一个核心改造的两个交付单元，不能只上线 A 后把 B 当作非必要工作。C 的接口可同时准备，但启用搜索必须经过真实 provider 验证；目前仓库没有可直接宣称已接好的通用搜索后端。没有搜索服务时，明确只提供当前可用的浏览器等能力。

每个交付单元使用独立回归、代表白名单和可追踪构建版本。运行协议版本在请求开始时固定；已有 v1 待审批任务按旧协议收尾，不能把旧任务半途按 v2 恢复。回退时不重放已发生的外部写入。

## 测试评估与覆盖图

现有 Vitest 已覆盖普通工具调用、部分来源检查、取消、审批等待、部分幂等/额度校验；目前存在“脚本化模型返回了期望工具即通过”的测试。它们不能证明真实模型在审批恢复后仍能完成原任务。

```text
新请求
  +-- 简单文本、无工具需求                    [已有；保持基线]
  +-- 动态目标/方法约束                       [新增 UNIT + EVAL]
        +-- 多工具候选，含强干扰工具           [新增 EVAL]
        +-- 用户指定/禁止某方法、组合任务       [新增 EVAL]
        +-- 额度/来源授权/能力拒绝              [已有底层；新增整链 E2E]
        +-- 执行与观察结果
        |     +-- HTTP 429/空页/错对象/过期数据 [新增 UNIT + EVAL + E2E]
        |     +-- 只读重试/写入结果未知         [复用测试并补跨恢复 E2E]
        +-- 等待审批                         [已有单次；恢复为关键缺口]
        |     +-- worker 重启/重复回调         [新增 E2E]
        |     +-- 第一次结果不足，第二次审批    [新增 E2E，关键回归]
        |     +-- 取消/撤权/额度释放            [已有底层；新增跨恢复 E2E]
        +-- 候选答复 → 完成条件核验             [新增 UNIT + EVAL]
              +-- 成功/部分成功/失败均诚实      [新增 E2E + EVAL]
```

评测样例应覆盖不同领域、同义表达、不同工具可用性和失败注入；工具集合保持相同，允许多条有效路径。重点指标是目标完成率、无关工具调用率、无依据成功声明、恢复后重复操作、审批轮次、端到端耗时及额度一致性。100 条测试数据可以验证通用能力，不把它们变成 100 条实现分支。

关键验收：给相同输入分别配置“直接读取可用、仅浏览器可用、有合适 MCP、只有不相关 MCP”，都应保持同一用户目标。无授权执行、重复写入和无依据成功声明在确定性回归中必须为零；真实模型指标与当前版本按相同模型、温度、工具目录和故障条件比较，保留未用于提示词调优的测试集。

## 性能与风险

- 避免为每一步强制增加独立 Planner 和 Reviewer 调用；普通问答保持当前快路径，工具任务按缺失证据有界评估。
- 大工具目录优先复用已发布描述与索引；现有规模不需要新增向量数据库或路由微服务。
- 大网页/文件保存到现有 Artifact，checkpoint 保存引用与有界摘要，避免每轮复制全部原文。
- 步骤、超时和模型预算必须跨审批恢复累计；等待人工的时间与实际执行耗时分开统计。
- 所有失败路径都需要明确用户结果。传输成功与业务完成分离会改变现有统计，应在协议版本内兼容，不能偷偷改变历史记录含义。

## 不在本次建议范围

- 行业专用工具和关键词表：与通用调度目标不符。
- 重建多 Agent 规划体系、替换 Pi：现有 SDK 已提供所需循环与钩子。
- 重新设计消费额度、账本、审批权限和知识隔离：复用已存在的授权边界。
- 绕过登录、验证码、网站限流：明确失败或换合法来源。
- 硬编码网站选择器/股票代码/地点：属于把评测样例写进实现。
- 全量重做界面：先让现有状态和最终结果准确；新增展示若需要应单独遵循 DESIGN.md。

## 工程评审记录

范围结论：选择现有单循环的增量修复，拆分交付以控制跨模块影响。
架构：5 项主要问题；代码质量：2 项；性能：3 项约束；测试：8 组补充覆盖已列入计划。
