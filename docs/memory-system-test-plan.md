# 代表记忆自动化测试与上线门禁

状态：代码门禁执行中

日期：2026-08-06

对应计划：[代表记忆自动化重构开发计划](./memory-system-plan.md)

## 1. 固定测试矩阵

建立 2 个代表、每个代表 2 个联系人、Web/Matrix/Telegram 三渠道，共 12 个会话单元。三种渠道都执行渠道内正向召回/提取和全量隔离测试；联系人跨渠道共享同时覆盖同一已验证身份加当前版本明确同意的正向路径，以及匿名、错绑、无同意、旧同意、撤回和跨代表/联系人等 fail-closed 路径。Matrix 必须覆盖首次披露、首条消息排除、绑定变更、provider edit/redaction 和删除恢复；Telegram 必须覆盖首次披露、首条消息排除、绑定变更、`edited_message`、`/forget`、`/delete_memory` 与精确删除命令。Telegram Bot 不可观测普通客户端消息删除，因此不得虚构或测试不存在的 provider 删除事件。

- 公开知识：只允许当前代表的活动发布版本；知识草稿、记忆开关和 OpenViking 联系人投影不得改变公开知识授权。
- 联系人记忆：默认只允许同一代表、联系人和来源渠道；只有同一已验证 `AudienceIdentity` 加有效同意时可跨渠道。
- 代表经验：只允许当前代表、已去标识化且达到多来源聚合阈值的当前版本。
- 短期记忆：只允许同一 conversation/episode，绝不写入 OpenViking。
- 交易和权限：无论记忆内容如何，付款、余额、退款、权益和授权始终以实时 PostgreSQL 为准。

## 2. 自动提取与决策

### 联系人记忆

- 白名单偏好、目标、约束和沟通方式能生成结构化、最小化总结，并记录自动策略版本、原因码、来源哈希和输出哈希。
- 姓名、邮箱、电话、用户名、平台 ID 等身份字段只写 Contact/Profile；语义记忆正文与投影中不存在这些字段副本。
- 相同事实重复出现返回 `NO_CHANGE`，不创建重复记忆或投影。
- 事实变化或用户纠正创建新版本，旧版本在同一事务内停止召回；乱序任务不能让旧值复活。
- 严格限定的“删除我的记忆”中英文命令只删除当前代表、联系人和当前来源渠道的联系人记忆；Telegram 同时提供 `/forget` 与 `/delete_memory`。广义或歧义删除文本 fail closed。Matrix 的 provider edit/redaction 与 Telegram 的 `edited_message` 会立即失效对应来源记忆；Telegram 普通客户端删除不可观测，用户必须使用 `/forget`、`/delete_memory` 或精确删除命令。保留到期和策略关闭同样立即阻断召回，并进入可重试清理。

### 代表经验

- 单条消息、单个联系人、单次 Handoff 和 Owner 私有备注均不能激活代表经验。
- 只有多个合格来源达到配置阈值后才能生成聚合经验；聚合文本不能还原联系人、会话或原文。
- 任一来源包含敏感内容、可逆标识或提示注入时，该来源被排除；剩余证据低于阈值时经验不得激活。
- 代表经验永不跨代表召回，联系人删除不得暴露其曾参与某条聚合经验。

### 失败关闭与安全语料

- 覆盖中英文凭据、Token、Cookie、私钥、电话、邮箱、证件、银行卡、地址、商业机密、支付/权益、Owner 私有备注、Compute/Tool 输出和持久化提示注入。
- 来源不允许、分类超时、提取异常、Schema 不合法、类别未知、置信度不足和策略版本未知时，只能 `BLOCK`、`QUARANTINE` 或 `RETRY`；生产投影和召回均为零。
- 审计事件不保存被阻止的敏感正文、原始对话或可逆个人标识。

## 3. 范围、短期与跨渠道

- 执行 12 x 12 全量交叉查询，验证零跨代表、跨联系人泄漏。
- 默认联系人记忆零跨渠道召回；只有 Owner 开启能力、各私聊解析为同一已验证 `AudienceIdentity`，且联系人接受当前披露合同并明确授权时，才允许生成、投影和召回 `CONTACT_SHARED` 安全摘要。
- 匿名、未验证、身份冲突、披露缺失、旧合同、旧策略版本、绑定变更和渠道开关关闭时保持渠道隔离，且不得查询 Provider 的共享范围。
- 授权重放保持同一同意版本；撤回立即阻断共享召回并异步删除投影；撤回后重新授权必须产生新同意版本，旧投影和旧授权不得复活。
- 短期开关开启时只加载当前 conversation/episode 的有界最近轮次；关闭、切换会话或 episode 后零加载。
- 短期上下文不创建候选、版本、OpenViking 资源或长期使用计数。

## 4. 生命周期、删除与权限

- 自动并发决策只有一个当前有效版本；重复投递和 ACK 前崩溃不产生重复资源。
- 停用、来源撤回、同意撤回、到期和删除提交后立即本地阻断；健康远端物理删除 p99 目标不超过 60 秒。
- 删除失败保持不可召回并自动/手动重试；删除证明只含对象标识哈希、范围、时间、策略版本、结果和错误分类，不含正文。
- 联系人只能影响自己的记忆与同意；Operator 只能读取当前服务必需的最小上下文；Owner 只能配置所属代表策略和查看只读健康摘要。
- 系统自动策略可以激活低风险记忆，但不能绕过来源、安全、身份、同意、范围、保留或删除栅栏。
- 记忆审批角色和人工批准/拒绝端点不存在或返回已退役结果；通用 Approvals 的 Action、Compute、支付与权限流程仍通过原权限测试。

## 5. 投影、同步与对账

- PostgreSQL 当前有效版本是唯一业务真相；伪造 URI、未知 URI、旧版本、staging、孤儿资源和仅存在于 OpenViking 的记录全部 fail closed。
- 每项投影使用 `provider + versionId + contentHash` 幂等键；部分成功保留成功项，只重试失败项。
- lease 超时恢复、worker 重启和旧 job 晚完成不能覆盖新 active version。
- 联系人/代表长期记忆可从 PostgreSQL 重建；短期记忆重建数和 Provider 写入数恒为零。
- 精确 URI 对账发现缺失、哈希不一致和旧 active pointer。Provider 不提供完整稳定库存快照时，库存覆盖必须显示“仅核对已知投影”；连接配置、运行同步和库存能力分别展示，不能把该能力限制误报为连接故障或最近运行错误，也不能自动删除未归属对象。
- 设置页同步状态、最后成功时间、积压、失败数和覆盖范围与真实账本一致，不显示硬编码健康值。

## 6. 使用账本与公开来源

- 分别验证 `SEARCH_HIT`、`SCOPE_ALLOWED`、`SAFETY_ALLOWED`、`PROMPT_INCLUDED` 和 `PUBLICLY_CITED`。
- Token 预算丢弃、策略阻断、生成失败和回复未提交不得计为“实际用于回答”。
- 展示来源必须是实际注入集合的子集；普通公开 DTO 不含 URI、Layer、Score、Session ID、其他联系人信息、原始 query 或内部策略原因。
- 没有已授权知识或记忆来源时，公开回复明确说明内容来自通用模型，不伪造知识库或记忆引用。

## 7. 设置、导航与产品边界

- Dashboard 顶层导航不存在“记忆系统”，旧 `view=memory` 在兼容期只重定向到当前代表 Memory 配置。
- 唯一 Owner 设置入口包含基础策略、Web/Matrix/Telegram 渠道能力、保留策略和只读高级诊断；保存具备严格校验、乐观并发、幂等、审计和 `private, no-store`。
- 缩短保留期限会把既有有效记忆的最晚到期时间同步压缩到新策略窗口；延长期限不会隐式延长旧记忆。
- 联系人跨渠道共享开关可由 Owner 启用，但页面必须说明这只是允许能力；没有同一已验证身份和联系人当前版本明确授权时仍按渠道隔离。API 保存、乐观并发、审计、关闭后的即时阻断与共享投影清理均需覆盖。
- 页面不出现候选列表、人工批准、拒绝、审核人、审核队列或“打开记忆系统”按钮。
- 知识库的导入、编辑、授权、草稿、发布、撤回、投影和公开问答测试结果与重构前一致。
- 通用 Approvals 导航、队列、授权和业务动作测试结果与重构前一致；不得因清理记忆审核代码而消失。
- Web/Matrix/Telegram 的产品能力与代表级启用状态分别展示；具体会话缺少首次披露、身份映射或删除边界时仍保持零召回、零提取、零越权 Provider 结果。

## 8. 迁移、兼容与清理

- additive migration 可在旧代码仍运行时部署；新代码可读取合法历史人工激活记录与新自动策略记录，但只写自动策略。
- 新代码稳定前回滚到旧应用时，自动提取默认关闭；已阻断、过期、删除和撤回同意的记录不能重新召回。
- 旧顶层页面重定向期间没有数据丢失；删除页面/API/DTO/样式后运行静态扫描，确认零生产引用、零死路由和零孤儿导出。
- 历史审核表和枚举只在独立 migration、完成归档且无旧应用回滚依赖后删除。
- 清理白名单明确排除知识库、公开知识投影、通用 Approvals、候选隔离、版本、自动策略审计、使用账本、删除证明和对账。

## 9. 回归、性能与灰度

- 运行 OpenViking、web-data、conversation-worker、bot、workflow-runner、Dashboard、公开代表页、知识库、Approvals 和 PostgreSQL 集成测试。
- 运行 `pnpm db:generate`、`pnpm db:validate`、全仓 typecheck、test、lint 和 production build。
- 召回 p95 相对“长期注入关闭”的基线增幅不超过 20%；自动决策审计和使用账本完整率至少 99.9%。
- Provider 超时、限流、损坏数据、数据库短暂断连和 worker 重启时，不发生跨范围泄漏、敏感激活、虚假引用或错误恢复旧版本。

```text
内部代表（自动提取/决策审计开启、长期注入关闭）
  -> 内部代表 Web
  -> Web 1%
  -> Web 10%
  -> 25%
  -> 50%
  -> 100%

Matrix/Telegram：从独立的“长期注入关闭”阶段开始，验证披露、首条排除、身份、删除和隔离门禁后再按代表逐步开启
```

任意跨代表/联系人泄漏、未同意跨渠道共享、敏感内容激活、删除后继续召回、交易/权限依赖记忆或公开内部字段，必须立即停止灰度。安全过滤、召回阻断和删除证明不能随功能回滚而关闭。
