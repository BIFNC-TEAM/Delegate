## Problem Statement

Delegate currently executes governed code and browser work through Docker containers created by `compute-broker` via the host Docker socket. The target architecture removes Docker from production execution while preserving it for local development and CI:

- Tencent Cloud AGSX is the China production provider.
- Daytona is the overseas production and rapid-PoC provider.
- Every `SandboxIdentity` is pinned to the provider selected when the identity is created.
- Phase 1 uses an explicit server-side manual override map. Geographic and tenant-policy routing are deferred.

The change must preserve Delegate's existing policy, approval, billing, audit, lease, and identity boundaries. A provider SDK must not become a second policy authority.

## What Makes This Useful

- Production code no longer requires a privileged Docker socket on the application host.
- Tencent and Daytona can be exercised side by side in one deployment.
- Provider selection is observable and deterministic instead of being inferred from client geography.
- The routing source can later change from a manual map to a policy engine without changing provider implementations or existing identity pins.

## Constraints

1. Provider choice is server-owned. Public requests, headers, IP geolocation, prompts, and tool arguments cannot select a provider.
2. Changing the manual override affects only identities created after the configuration change.
3. Existing identities never fail over to another provider automatically.
4. Provider migration is not part of Phase 1. It will be a separate explicit, audited operation.
5. Provider-local root filesystems are not durable product storage. Durable inputs and outputs use the existing S3-compatible artifact/object-store layer.
6. Docker remains available only for development and CI. Production configuration rejects Docker for new identities without an exception path.
7. Provider adapters must enforce parity for every network, filesystem, timeout, working-directory, lifecycle, and output-size capability enabled for that provider/runtime class.
8. Secrets are passed through provider-specific secret facilities and never stored in audit payloads, labels, commands, or sandbox metadata.

## Premises

1. The identity key is the existing `representativeId + contactId + scopeKey` tuple. Its stored `provider` is authoritative after creation.
2. A provider outage causes a retryable provider-specific failure for the pinned identity; it does not cause cross-cloud execution.
3. The Phase 1 override source is deployment configuration, not Dashboard UI or representative publishing state.
4. A rolling deployment may contain old and new routing configuration at the same time. A unique identity row created by either process wins, and all losing requests must reuse its stored provider.
5. Provider availability for existing pinned identities is separate from admission for new identities. Disabling new Tencent identities does not remove the Tencent adapter or credentials needed by existing Tencent identities.
6. Phase 1 is a code-only, test-representative PoC. It is not a production cutover and does not claim browser, workspace, billing-reconciliation, or data-residency parity.

## Phase 0/1 Implementation Scope

This document authorizes only the following implementation:

### Phase 0: Contract and identity hardening

- Make the stored identity provider immutable during ordinary acquisition.
- Add the provider registry and typed provider error taxonomy.
- Correct Daytona's code-execution network, working-directory, and timeout mappings.
- Add shared code-runtime contract tests.

### Phase 1: Manual dual-provider code PoC

- Parse one server-owned routing document containing default, representative overrides, and new-identity admission flags.
- Reject every new-identity creation whose representative is not in the Phase 1 test allowlist before insertion.
- Add the Tencent provider kind and a Tencent code-runtime spike/adapter.
- Run only dedicated non-customer test representatives with `ephemeral_full` and no durable workspace hydration.
- Collect comparable lifecycle, latency, error, orphan, and provider-cost telemetry.

The following require separate follow-on designs before implementation: browser parity, provider-neutral workspace transport, reconciliation beyond the Phase 1 creation journal, production billing reconciliation, customer-data residency, explicit provider migration, and production Docker cutover.

## Existing System to Reuse

- `SandboxIdentity` already stores a provider and is unique by representative, contact, and scope.
- `SandboxLease` already stores provider runtime handles and lifecycle state.
- `SandboxProvider` already defines `start`, `execute`, `stop`, and `delete` operations.
- Docker and Daytona providers already implement that interface.
- Lease cleanup, audit events, metrics, billing, and compute-session fencing already exist.
- The artifact store already exposes an S3-compatible persistence boundary.
- `SANDBOX_IDENTITY_CREATED`, `SANDBOX_LEASE_STARTED`, `SANDBOX_LEASE_STOPPED`, and `SANDBOX_LEASE_ERRORED` event types already exist.

The existing code must be corrected before adding Tencent: `ensureUserSandboxLease` currently includes `provider` in the update side of the identity upsert, so a later request can overwrite an existing identity's provider. The new design makes the stored provider immutable during ordinary lease acquisition.

## Approaches Considered

### Approach A: Deployment-Wide Default Only

Configure one `SANDBOX_PROVIDER_DEFAULT` value and restart the service to switch all newly created identities.

- Smallest implementation.
- Requires redeployment for every comparison.
- Cannot exercise Tencent and Daytona concurrently in one environment.
- Makes it harder to distinguish configuration effects from provider effects.

### Approach B: Default Plus Representative Override Map

Configure a default provider, an allowlisted map keyed by immutable representative ID, and separate new-identity admission flags.

```json
{
  "version": 1,
  "default": "tencent",
  "newIdentityEnabled": {
    "docker": false,
    "daytona": true,
    "tencent": true
  },
  "phase1AllowedRepresentativeIds": [
    "cm_rep_daytona_test",
    "cm_rep_tencent_test"
  ],
  "representatives": {
    "cm_rep_daytona_test": "daytona",
    "cm_rep_tencent_test": "tencent"
  }
}
```

- Supports side-by-side testing in one deployment.
- Keeps routing server-owned and reviewable.
- Adds no product UI or published-version semantics.
- Evolves cleanly into a later policy-based selector.

### Approach C: Dashboard Provider Selector

Add a provider control to representative configuration.

- Convenient for operators.
- Prematurely introduces UI permissions, draft/published semantics, validation, and user-visible cloud implementation details.
- Makes an infrastructure test control look like a product capability.

## Recommended Approach

Use Approach B.

### Configuration

Use one authoritative routing document with strict startup validation:

```bash
SANDBOX_PROVIDER_ROUTING_JSON='{
  "version": 1,
  "default": "tencent",
  "newIdentityEnabled": {
    "docker": false,
    "daytona": true,
    "tencent": true
  },
  "phase1AllowedRepresentativeIds": [
    "cm_rep_daytona_test",
    "cm_rep_tencent_test"
  ],
  "representatives": {
    "cm_rep_daytona_test": "daytona"
  }
}'

DAYTONA_API_KEY=...
DAYTONA_API_URL=...
DAYTONA_TARGET=...

TENCENT_AGS_REGION=ap-guangzhou
TENCENT_AGS_API_KEY=...
TENCENT_AGS_CODE_TOOL=delegate-code-v1
```

Rules:

- Static startup validation rejects unsupported versions, unknown or non-lowercase provider values, duplicate raw JSON keys, malformed JSON, more than 1,000 overrides, invalid representative-ID formats, and a default/override whose new-identity admission flag is false.
- Database-backed readiness validation requires every Phase 1 allowlisted representative to exist, be active, have server-only `sandboxTestEligible=true`, and include every override key. Missing, archived, deleted, customer, or non-test representatives make readiness fail. The flag is set only by seed/operations tooling and is never owner-editable or publishable.
- For identities that do not yet exist, Phase 1 requires the representative to be in `phase1AllowedRepresentativeIds`; all other creation attempts fail with `sandbox_phase1_representative_not_allowed` before insertion. The allowlist does not reroute or mutate an identity that already exists.
- Provider adapters can be configured while disabled for new identities. Existing identities may continue using a configured disabled provider.
- Production rejects `docker` as the default, an override, or an enabled new-identity provider.
- Missing credentials never trigger fallback. Static absence is a startup configuration error; invalid credentials or remote capability/quota probe failure makes readiness degraded and blocks new identity creation for that provider without killing liveness.
- Secrets are supplied through the deployment secret manager rather than committed environment files.

The routing decision audit stores `sha256` over RFC 8785/JCS canonical JSON for the non-secret routing document, prefixed with schema version `routing:v1:`. Provider credentials and endpoints are excluded.

### Configured versus admitted providers

```text
configured adapter + valid credentials
        |
        +-- newIdentityEnabled=true  --> existing pins + new identity admission
        |
        +-- newIdentityEnabled=false --> existing pins only
```

Database/provider-reference readiness polls every 60 seconds and queries the distinct providers referenced by identities whose status is exactly `ACTIVE`; this local result is valid for at most 90 seconds. Remote credential/Tool capability probes use a separate five-minute cache. A request always rechecks local adapter configuration and requires both a fresh local reference result and a non-expired successful remote probe for its authoritative provider, using single-flight refresh when either is stale. If an adapter is not configured, the broker remains live but reports `pinned_provider_unavailable` and refuses those identities explicitly.

Disabling admission is one atomic routing-document change: first move `default` to an enabled provider and remove or reroute affected overrides, then set the old provider's `newIdentityEnabled` flag to `false` in the same document. A disabled provider may not remain a default or override target.

### Provider Selection and Pinning

```text
Compute request
    |
    v
Load identity by (representative, contact, scope)
    |
    +-- exists -----------------------------------+
    |                                              |
    |                                  use identity.provider
    |                                              |
    +-- absent --> resolve manual override/default|
                     |                             |
                     v                             |
                 INSERT identity -----------------+
                     |
                     +-- unique race --> reload winner
                                             |
                                             v
                                create/reuse same-provider lease
                                             |
                                             v
                                  providerFactory(identity.provider)
```

Ordinary lease acquisition must never update `SandboxIdentity.provider`. The provider argument is removed from call sites after identity reservation; the provider factory is invoked from the provider stored on the winning identity row.

The request uses this decision order:

1. Look up the identity tuple without mutation.
2. If it exists, validate its status and the stored provider's adapter/readiness only. Current allowlist, default, overrides, and new-identity admission flags do not apply.
3. If absent, capture one validated routing document version/digest, enforce the Phase 1 representative allowlist, resolve the provider, and check that provider's new-identity admission/readiness.
4. Enter the conflict-safe reservation transaction. If a concurrent creator wins, use the winner's stored provider and recheck that provider's adapter/readiness without rerouting.

The reservation transaction then uses these exact semantics:

1. `SELECT ... FOR UPDATE` the identity by its unique tuple.
2. If it exists and is `ACTIVE`, use its stored provider. `ARCHIVED` or `DELETED` identities are not silently reactivated.
3. If absent, resolve the manual routing document and run `INSERT ... ON CONFLICT DO NOTHING` with the selected provider.
4. Reload the unique row in the same transaction and treat its provider as authoritative, even if it differs from the process-local selection.
5. Insert the `STARTING` lease only while the locked identity is still `ACTIVE`, and capture its `lifecycleEpoch` on the lease.
6. If the row disappears because of a concurrent administrative delete, retry the complete transaction at most three times with bounded jitter, then return `sandbox_identity_concurrent_change`.

Add `SandboxIdentity.lifecycleEpoch Int @default(1)`. Administrative archive/delete operations lock the same identity row, increment the epoch, change status, and cancel/stop every `STARTING` or `RUNNING` lease. After a remote start returns, binding succeeds only through a conditional transaction that requires identity `ACTIVE`, the captured epoch unchanged, and the lease still `STARTING`. If the fence is lost, the new remote runtime is immediately stopped/quarantined and the request returns `sandbox_identity_concurrent_change`.

PostgreSQL `READ COMMITTED`, row locking, lifecycle epoch, and the unique constraint together define the serialization boundary. If provider readiness degrades after identity insertion, the identity remains pinned and the request returns a same-provider typed error; it is never rerouted.

Inactive identity outcomes are explicit:

- `ARCHIVED` -> `sandbox_identity_archived`
- `DELETED` -> `sandbox_identity_deleted`

The caller may use a genuinely new server-generated scope only through the normal product flow; it may not bypass an inactive identity by supplying a scope key. Reactivation requires an administrative operation.

Only the transaction whose `INSERT ... RETURNING` succeeds records `SANDBOX_IDENTITY_CREATED`, in the same transaction, using the winning stored provider and that process's decision source/digest. Conflict losers do not emit a creation event. The event contains:

- sandbox identity ID
- selected provider
- decision source: `manual_override` or `default`
- representative ID
- scope type, without contact content
- a digest of the routing configuration, not the raw configuration

### Remote creation idempotency

Each remote creation has a durable operation-journal record created before the provider call. Its key is:

```text
sha256("delegate-sandbox-create:v1:" + sandboxLeaseId + ":" + attemptNumber)
```

The key is sent through the provider's native idempotency token when supported and is also represented by a deterministic remote name or provider-safe label. The minimum label/metadata schema is:

```text
delegate.sandbox_identity_id
delegate.sandbox_lease_id
delegate.creation_key
delegate.runtime_class
```

An ambiguous create result is never blindly retried. The operation becomes `UNKNOWN`; reconciliation first searches by native idempotency key, deterministic name, or labels. If lookup is unsupported or eventually inconsistent beyond the bounded reconciliation window, the lease is quarantined and cannot execute. Duplicate remote runtimes are stopped and deleted only after one canonical runtime is transactionally bound and no execution references the duplicates.

The journal is an explicit model, not an audit-event reconstruction:

```text
SandboxProviderOperation
  id
  sandboxLeaseId
  attemptNumber
  creationKey
  provider
  operation = CREATE
  state = PENDING | CALLED | BOUND | UNKNOWN | FAILED | QUARANTINED | RESOLVED
  providerOperationId?
  providerSandboxId?
  ownerTokenHash?
  ownerLeaseExpiresAt?
  deadlineAt
  lastErrorCode?
  createdAt / calledAt? / resolvedAt? / updatedAt

UNIQUE(sandboxLeaseId, attemptNumber, operation)
UNIQUE(creationKey)
```

State transitions:

```text
PENDING -> CALLED -> BOUND -> RESOLVED
   |          |         |
   +-> FAILED <-+       +-> FAILED
              |
              +-> UNKNOWN -> BOUND/QUARANTINED/FAILED -> RESOLVED
```

`FAILED` records a sanitized typed failure code and is used only when the provider definitively proves that no runtime was created, or when a bound runtime later fails terminally. Auth/config/policy failures do not retry. A retryable definitive create failure marks the current lease `ERROR` and, within the persisted retry budget, creates a new lease row with a new journal attempt; it never reuses the failed creation key. Ambiguous failures remain `UNKNOWN`, never `FAILED`, until reconciliation proves an outcome.

Reconcilers claim work with a hashed owner token and expiring database lease. A crashed owner becomes reclaimable after expiry. Journals are retained for at least 30 days after `RESOLVED` or terminal `FAILED`; unresolved and quarantined records are never age-deleted. A provider without bounded lookup by native idempotency token, deterministic name, or metadata fails the Phase 1 spike.

### Provider Registry

Extend the provider kind to:

```text
docker | daytona | tencent
```

Use one explicit registry/factory rather than provider-specific branching across leases, executions, cleanup, and browser code:

```text
provider kind --> provider factory --> normalized SandboxProvider contract
```

The registry owns credential readiness and adapter construction. Provider adapters own only remote runtime operations. Delegate continues to own admission, policy, billing, audit, and lifecycle truth.

### Normalized Contract

Phase 0 defines explicit request/response semantics rather than a lowest-common-denominator SDK wrapper:

```ts
type SandboxRuntimeClass = "code" | "browser";

type SandboxStartRequest = {
  identityId: string;
  leaseId: string;
  creationKey: string;
  runtimeClass: SandboxRuntimeClass;
  network: { mode: "no_network" | "allowlist" | "full"; allowlist: string[] };
  filesystem: { mode: "workspace_only" | "read_only_workspace" | "ephemeral_full" };
  lifecycle: { idleStopMinutes: number; absoluteTtlMinutes: number };
};

type SandboxExecuteRequest = {
  providerSandboxId: string;
  command: string;
  workingDirectory: string;
  timeoutMs: number;
  maxStdoutBytes: number;
  maxStderrBytes: number;
};

type SandboxExecuteResult =
  | {
      termination: "exit";
      exitCode: number;
      stdout: string;
      stderr: string;
      wallMs: number;
    }
  | {
      termination: "command_timeout" | "output_limit";
      exitCode: null;
      stdout: string;
      stderr: string;
      wallMs: number;
    };
```

The provider registry, not the request or caller, resolves runtime class to trusted image/snapshot/Tool configuration. Working directories must be normalized absolute sandbox paths under the provider workspace root; traversal, symlink escape, and nonexistent-directory inputs fail before command execution. Timeout is end-to-end command wall time in milliseconds, distinct from provider HTTP transport timeout. Output-limit termination is a failure and is never reported as a successful truncated result.

Stdout and stderr have independent byte limits applied to raw streamed bytes before UTF-8 decoding and redaction. Providers must stream output or enforce an equivalent provider-side cap; buffered post-hoc truncation does not satisfy the contract. Invalid UTF-8 is decoded with the standard replacement character after the byte limit is enforced. On timeout/output-limit termination, already captured bounded partial output may be returned for private diagnostics, but the execution is terminal failure and the partial output is not published as a successful result.

Phase 1 has no secret injection and no customer credentials. Adding opaque secret references or provider secret resolution requires a separately reviewed contract. Raw secrets remain categorically forbidden in start/execute requests.

`stop` and `delete` are idempotent: already-stopped satisfies `stop`; already-deleted/not-found satisfies `delete`. The lifecycle state machine is:

```text
STARTING -> RUNNING -> STOPPING -> STOPPED -> STARTING
    |          |          |          |
    +----------+----------+----------+--> ERROR/QUARANTINED
STOPPED/ERROR/QUARANTINED ----------------> ARCHIVED/DELETED
```

Before either cloud provider can be enabled beyond Phase 1, contract tests must prove:

- start new runtime
- restore stopped runtime
- execute with working directory
- enforce command timeout
- return exact exit code, stdout, stderr, and wall time
- stop without deleting durable identity data
- delete idempotently
- enforce required modes for the enabled runtime class
- cap output and redact provider errors
- preserve provider runtime ID across lease reuse

For the Phase 1 code PoC, `ephemeral_full` and `no_network` are mandatory; `allowlist`, `full`, workspace-backed modes, and browser class are disabled at admission. A provider may reject optional modes, but a provider cannot be marked ready for a released production capability until it implements every mode that capability's policy can authorize.

Daytona currently needs hardening: network fields are not mapped to Daytona's real firewall parameters, and working directory and command timeout are ignored. These are Phase 0 blockers, not follow-up polish.

### Typed provider errors and retry ownership

Adapters return sanitized typed errors:

| Error | Retry policy |
|---|---|
| `THROTTLED` | lifecycle orchestrator retries with provider-aware backoff and jitter |
| `TRANSPORT_TIMEOUT` | retry only idempotent reads/stops; create becomes `UNKNOWN` |
| `REMOTE_5XX` | bounded retry for idempotent operations; create uses reconciliation |
| `AUTH_INVALID` | non-retryable; readiness degraded |
| `CONFIG_INVALID` | non-retryable; startup/readiness failure according to validation phase |
| `POLICY_UNSUPPORTED` | non-retryable; reject before execution |
| `RUNTIME_NOT_FOUND` | mark the old lease `ERROR`; create a new lease row on the same pinned provider with attempt 1 |
| `COMMAND_TIMEOUT` | terminal execution result; do not rerun side effects |
| `AMBIGUOUS_CREATE` | no direct retry; reconcile by creation key |

Adapters do not retry internally. The lifecycle orchestrator owns retry counts and backoff so billing, audit, fencing, and duplicate prevention observe every attempt.

Bounded policy:

- idempotent describe/read/stop: at most 3 attempts, exponential backoff with full jitter from 250 ms capped at 2 seconds
- delete: at most 3 attempts; not-found is success
- create: one provider call per journal attempt; ambiguous results go to reconciliation rather than direct retry
- reconciliation lookup: at most 8 attempts over a persisted two-minute deadline unless the provider spike proves a longer minimum-consistency window, in which case Phase 1 is blocked pending explicit review
- command execution: never automatically retried after dispatch

Every retry deadline is persisted and also bounded by compute-session expiry. Process restarts resume the remaining budget rather than resetting it.

### Tencent AGSX Spike and Adapter

Phase 1 first runs a live spike against one pre-created `delegate-code-v1` tool. The spike must prove or disprove these hypotheses with captured request IDs and sanitized evidence:

- instance creation supports a stable idempotency token, deterministic name, or searchable metadata
- a stopped instance can be restored within the configured lifetime
- command execution returns exit code, stdout, stderr, and enforceable timeout semantics
- command output is streamed or capped provider-side before Delegate's byte limit
- `SANDBOX` mode blocks all tested egress, including IPv4, IPv6, and DNS
- instance lookup can reconcile an ambiguous create result
- lifecycle APIs expose states that can be mapped without inventing success
- non-destructive readiness probes can validate credentials, tool presence, and capability

Only hypotheses that pass become `TencentAgsxSandboxProvider` behavior. Failed hypotheses are recorded as blockers or mapped to an explicit `POLICY_UNSUPPORTED`; they are not papered over with client-side assumptions.

For the Phase 1 code PoC, the adapter maps the logical `code` runtime class to `delegate-code-v1`, maps `no_network` only after the egress test passes, maps provider runtime ID to Tencent Instance ID, and keeps Tencent request IDs in private operational logs.

The spike must output the exact least-privilege API Key/CAM permission manifest, including required create, describe, execute/command, start, stop, delete, token, and metadata/list actions. The final role is generated from observed API calls and then tested with an explicit denied-extra-action check.

Browser Tool mapping, `PUBLIC`/VPC egress, allowlists, and All-In-One are follow-on designs.

Daytona must pass the same live Phase 1 spike. SDK parameter presence is insufficient: the smoke evidence must prove actual no-network behavior, working-directory enforcement, hard command timeout, bounded/streamed output, lookup after ambiguous create, stop/restart, and idempotent delete in the selected Daytona region.

### Runtime Class

Provider selection and runtime selection are separate decisions:

```text
Provider:      docker | daytona | tencent
Runtime class: code | browser
```

Do not infer runtime class from a mutable image tag. Add an immutable `SandboxRuntimeClass` enum (`CODE`, `BROWSER`) to `ComputeSession` and `SandboxLease`; set it from the server-validated requested capabilities when the session is created and copy it into every lease. Provider configuration maps the logical class to an image, snapshot, or Tencent Tool ID.

All-In-One is deferred. Code and browser remain separate least-privilege classes, with artifacts passed through provider-neutral storage.

### Provider-Neutral Workspace Follow-On Gate

Cloud sandboxes cannot bind-mount the Delegate host workspace. Production cloud execution therefore uses this flow:

```text
authorized inputs
      |
      v
S3/COS object manifest --hydrate--> ephemeral sandbox workspace
                                      |
                                      v
                              governed execution
                                      |
                                      v
approved outputs <--------- collect + hash + upload
```

Phase 1 supports synthetic `ephemeral_full` fixtures only and does not hydrate customer workspaces.

A separate workspace-transport design is required before production cutover. At minimum it must define:

- versioned manifest schema and canonical checksum
- owner/representative/contact/object-key tenancy rules
- authorized input selection and output allowlist
- broker-mediated upload/download or short-lived scoped URLs; long-lived COS/S3 credentials are never injected into the sandbox
- normalized paths plus symlink, hardlink, traversal, archive-bomb, decompression-ratio, file-count, and byte limits
- two-phase output commit so partial uploads are not published
- idempotent hydration/collection and cleanup after provider loss
- region-local storage topology and an explicit prohibition on unapproved China/overseas artifact transfer

### Manual Test Procedure

Use two dedicated representatives in the same deployment:

- Tencent test representative mapped to `tencent`
- Daytona test representative mapped to `daytona`

Changing the override map does not move existing identities. To test a new selection, create a new scoped test identity/conversation or use a future explicit migration command. Never edit the provider column manually while leases exist.

### Schema migration and existing Docker identities

Phase 0 adds `TENCENT` to `SandboxProviderKind`; adds server-only `Representative.sandboxTestEligible`; adds `SandboxIdentity.lifecycleEpoch`; adds `SandboxLease.identityLifecycleEpoch`; creates `SandboxProviderOperation` and its state enum; and adds non-null `runtimeClass` fields to sessions/leases. `CODE` is the conservative runtime-class backfill only for records that are provably non-browser. Browser records are backfilled to `BROWSER`; ambiguous rows are quarantined for operator review rather than guessed.

Existing non-null `DOCKER` identities remain Docker-pinned. Development and CI continue to run them. A later production-cutover migration must decide whether each active Docker identity is migrated, archived, or explicitly marked migration-required. Phase 1 does not rewrite or reactivate them, and production cloud-only execution returns `sandbox_provider_migration_required` if one is encountered.

### Audit and PoC cost accounting

Every provider lifecycle attempt records provider kind, runtime class, creation key, attempt number, sanitized provider operation/request ID, outcome class, and wall time. Raw payloads, secrets, commands, customer content, and provider exception bodies are excluded.

Phase 1 runs only non-customer test representatives and does not alter customer billing. Provider invoice/cost observations are stored as PoC operational metrics separate from Delegate billable units. Production provider-cost reconciliation, duplicate-runtime charging, partial-execution billing, and customer ledger semantics require a follow-on billing design.

### Rollout

```text
Phase 0  Provider contract hardening + immutable identity pin
   |
Phase 1  Manual override router + Tencent code PoC + Daytona code PoC
```

Phase 1 comparison uses only synthetic and explicitly read-only fixtures. It never duplicates a customer task or external side effect across clouds.

New-identity admission is reversible through one atomic routing-document update that reroutes the default/removes affected overrides and disables the failing provider for new identities, while keeping its adapter and credentials available to existing pins. Already pinned identities are not made reversible by this design; they require provider recovery or a future explicit migration operation.

Follow-on designs, each separately reviewed, cover browser parity, workspace transport, production reconciliation/billing, canary cutover, and eventual signed region/tenant policy routing.

## Failure Modes

| Failure | Required behavior |
|---|---|
| Override changes during rolling deploy | Unique identity insert winner pins provider; loser reloads it |
| Existing pin's provider is disabled for new identities | Existing pin continues through its configured adapter |
| Existing pin's adapter/credentials are missing | Readiness reports `pinned_provider_unavailable`; execution fails explicitly |
| Provider credentials missing | Startup/readiness fails for configured provider |
| Tencent or Daytona outage | Pinned identity reports retryable provider failure; no cross-cloud fallback |
| Provider start succeeds but DB update fails | Operation journal becomes `UNKNOWN`; reconciliation discovers by creation key and repairs or quarantines it |
| Concurrent identity delete during creation | Retry transaction at most three times, then return explicit conflict |
| DB lease exists but remote sandbox is gone | Mark lease error, create a new lease on the same provider |
| Cleanup stop times out | Keep lease non-runnable/error and retry idempotently |
| Network policy cannot be represented | Fail before remote execution |
| Output exceeds limit | Terminate/mark failed; do not persist truncated output as success |
| Config points code and browser to same wrong tool | Readiness probe fails capability contract |
| Existing Docker identity reaches production | Block execution and surface migration-required status |
| Secret appears in provider error/output | Redaction gate replaces it and records a security failure without persisting the secret |

## Test Strategy

### Unit and Contract Tests

- Parser accepts valid default/override configuration and rejects malformed, unknown, or credential-incomplete configuration.
- When the identity is absent, the Phase 1 allowlist rejects non-test representatives before insertion; existing pins bypass creation routing and keep their provider.
- Existing identity provider wins over a changed override.
- New identity uses representative override before default.
- Concurrent creation with different configuration converges on one stored provider.
- Archived/deleted identities are not silently reactivated; concurrent deletion follows the bounded conflict path.
- Archive/delete racing with remote start loses the lifecycle-epoch bind fence and cleans up/quarantines the remote runtime.
- Provider mismatch between identity and lease is rejected.
- Production Docker selection is rejected.
- Missing provider credentials never fall back.
- Disabling new identities leaves existing pinned identities executable.
- Atomic reroute-and-disable configuration validates while a disabled default/override target does not.
- Active identities whose adapter is missing make readiness degraded.
- Daytona maps network, timeout, and working directory correctly.
- Tencent maps tool, instance, network, timeout, lifecycle, and errors correctly.
- Every provider passes the shared normalized contract suite.
- Secret canaries never appear in command serialization, environment dumps, labels/metadata, stdout/stderr snapshots, exceptions, metrics, or audit payloads.

### Integration Tests

- Database transaction and unique-race test using PostgreSQL.
- Fake-provider lifecycle test covering create, reuse, stop, loss, and delete.
- Provider API fault injection: timeout, 429, 5xx, malformed response, vanished instance, and duplicate request.
- Creation-journal test covering ambiguous success, delayed lookup, duplicate resolution, quarantine, and cleanup.
- Creation-journal crash/reclaim test covers every allowed state transition—including definitive `FAILED` versus ambiguous `UNKNOWN`—unique key, owner-lease expiry, deadline, new-lease retry, and retention behavior.

For both Tencent and Daytona code runtimes:

- cold create and `echo` execution
- warm reuse
- Python and Node execution

- independent stdout/stderr output-limit enforcement
- no-network exfiltration attempt

Cost is a clearly labeled estimate calculated from provider-published CPU, memory, storage, and runtime rates using the configured resource reservation and measured billable duration; invoice reconciliation is deferred. Vendor marketing latency is not an acceptance criterion.

The Tencent readiness probe is non-destructive: authenticate, describe the configured Tool, and inspect declared capability metadata without creating an instance. Results are cached for five minutes with single-flight refresh and provider rate-limit backoff. Live create/execute checks run only as explicit smoke jobs.

## Success Criteria

1. The same deployment runs dedicated Tencent and Daytona code test representatives concurrently.
2. In race tests and 1,000 repeated acquisitions, zero ordinary requests change an existing identity's provider.
3. Fault injection proves zero silent cross-provider or Docker fallbacks.
4. All Phase 1 code-runtime contract tests pass for both clouds.
5. One hundred sequential and twenty concurrent synthetic executions per provider achieve at least 99% success, excluding deliberately injected failures.
6. Phase 1 `no_network` exfiltration tests have zero successful IPv4, IPv6, or DNS egress attempts.
7. Cold-start p95 is at most 5 seconds and warm command-dispatch overhead p95 is at most 500 ms in the chosen test regions; results outside the gate block promotion but may revise the budget through an explicit review. Record broker/provider regions, five excluded warm-up runs, provider quota state, runtime resource class, image/Tool revision, and nearest-rank percentiles over at least 100 measured runs so results are reproducible.
8. Ambiguous-create and provider-loss fault tests converge within five minutes to zero runnable duplicates; every unresolved provider-side runtime is represented by a non-runnable `QUARANTINED` journal/lease and is reported separately until provider lookup permits cleanup. Bounded lookup is a hard spike prerequisite.
9. Audit and metrics attribute every attempt to provider, runtime class, and sanitized creation key, while secret-canary scans find zero leaks.
10. Telemetry reports startup, command overhead, typed errors, orphan convergence, and estimated provider cost per successful synthetic task with its rate-card version.
11. Local development and CI continue to use Docker; Phase 1 makes no production cutover claim.
