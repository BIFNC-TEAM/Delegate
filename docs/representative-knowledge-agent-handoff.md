## 4. #1 FAQ生成：请同事具体做什么

### 用途与交互

创建者选资料，让AI整理“访客可能会问什么、根据资料可以怎样回答”。结果先进入候选列表，由创建者检查和编辑，再决定采用。生成成功不能自动写入正式FAQ或发布。

例如产品资料明确写了“周一到周五提供支持”，可以生成服务时间问答；资料没写退款政策，就不能编出“支持7天退款”。没有足够材料时应说明不足或返回空候选。

### 已有接口（实际代码，不是新建议）

`POST /api/dashboard/faq-suggestions`，浏览器同源调用，需要Delegate登录会话。开发环境用当前站点地址，生产也同源，不硬编码某台机器域名。模型凭据只由服务端读取，不能让前端持有。

请求示例：

```json
{
  "assetIds": ["asset-id-1"],
  "count": 3,
  "representative": { "name": "产品顾问", "description": "介绍产品和服务" }
}
```

- `assetIds`：所属账号有权读取的知识文件ID；服务端检查归属与可用性。
- `count`：当前实现是每份资料期望生成数量，不是整次总数量。前端传3。
- `representative`：可选，提供名称与描述；不是授权依据。
- API最多接受20个ID，但实际只取前5份，每份正文前2000字符；前端也限制5份。描述最多接受2000字符，实际上下文截到500字符。
- API按可用资料数量限制请求count，总量预算50；描述非空时另加“当前代表有什么功能或作用？”候选，因此不要假设最终返回恒定3条。

返回形状示例（仅展示主要字段）：

```json
{
  "status": "success",
  "suggestions": [
    { "question": "支持时间是什么？", "answer": "周一到周五。", "sourceIds": ["asset-id-1"] }
  ],
  "results": [
    { "id": "asset-id-1", "title": "服务说明", "updatedAt": "2026-11-24T00:00:00.000Z", "processingVersion": 1, "status": "success", "usage": "complete", "suggestions": [] }
  ],
  "ignoredAssetIds": [],
  "descriptionTruncated": false
}
```

示例只说明结构；真实results中的suggestions应与该份资料产出一致。顶层状态有success、partial_success、failed、no_usable_sources；单份还有insufficient_material、timeout、model_failure等，详见types与route。HTTP 200不保证所有资料都生成成功，必须读业务状态。401为未登录，400为参数/资料不可用等，500为未能处理请求。

### 请先核对并补齐的内容

1. 阅读现有 `generateFaqSuggestions`，不要新造平行生成接口。确认当前资料数量、截断方式是否满足FR1.2.3；若不足，给出需要调整的范围与耗时影响，由双方同步前后端限制和提示。
2. 每条候选必须有可核对的来源ID，资料不足不补造事实；某一份失败时保留其他成功候选。
3. 对齐长度限制：模型候选schema目前问题最长500，而新版编辑/保存只接受100字，答案2000字。应统一生成与保存的可接受长度，避免“生成成功却无法采用”；中文字符计数口径也要统一。
4. 确认超时/模型失败/无有效出处等返回被前端正确展示，不只返回一条含糊错误。前端当前180秒中止等待，不代表后台一定取消了模型任务。
5. 不开发语义去重。重复问题的最终入库校验由我们负责；同题不同答案也不能静默覆盖已有答案。

### 联调和验收

- 我们先提供测试账号、测试代表和已READY的测试资料；同事使用测试模型配置，不在Git或文档发密钥。
- 使用真实API测试：资料充足、材料不足、空正文、单份失败多份成功、超时、未登录、跨账号文件、长问题输出。

## 5. #5 服务边界：请同事具体做什么

### 实际场景和预设

| 规则ID | 场景 | 当前默认动作 |
| --- | --- | --- |
| appointment | 见面与会议安排 | approve，需要我审批 |
| discount | 特殊报价与折扣 | approve，需要我审批 |
| scope | 额外交付与承诺 | approve，需要我审批 |
| dispute | 投诉与争议 | handoff，需要我接手 |
| human | 希望与你本人交流 | handoff，需要我接手 |

创建者可以改动作，也可增加自定义规则；第三种动作是decline，不提供此类服务。预设规则的request可以为空，Agent不能因此认为没有规则，应按规则ID解释其场景；自定义request不能为空。

用户问“多少钱”是正常价格咨询；“能打八折吗”才可能触发折扣规则。要避免把普通咨询或一般计划建议误判成必须审批/转人工。

### 当前草稿数据（已实现）

`GET/PATCH /api/dashboard/representatives/[slug]/setup`中的`knowledgeSettings`，示意如下：

```json
{
  "version": 1,
  "files": [{ "id": "asset-id-1", "allowDownload": false }],
  "featuredFaqIds": ["faq-id-1"],
  "faqSources": { "faq-id-1": "服务说明" },
  "boundaries": [
    { "id": "appointment", "request": "", "action": "approve" },
    { "id": "discount", "request": "", "action": "approve" },
    { "id": "scope", "request": "", "action": "approve" },
    { "id": "dispute", "request": "", "action": "handoff" },
    { "id": "human", "request": "", "action": "handoff" },
    { "id": "custom-example", "request": "不提供代运营服务", "action": "decline" }
  ]
}
```

这里只是完整setup中的一个字段，不能把它当成完整PATCH请求。FAQ正文沿用 `knowledgePack.faq`，人工说明沿用 `handoffPrompt`，评估时窗沿用 `contract.handoffWindowHours`。`faqSources`目前是展示标签，不应当作Agent的可验证证据正文。

### Agent和我们各负责什么

Agent侧：读取发布后的规则，理解本轮请求，命中具体规则；缺少必要信息时补问；调用已有审批/转人工能力；根据真实回执回复。未命中规则的普通咨询正常处理，用户让它“忽略规则”不能绕过边界。

我们侧：提供配置和发布数据、鉴权与业务接口、审批/接待记录、状态展示、幂等和权限检查。支付及人工权益由业务系统决定，不由模型口头决定。

审批成功创建后才能说“已提交”，不等于已批准；转人工请求已登记不等于真人已加入；拒绝动作不应产生审批记录。评估时窗不等于交付承诺。

### 联调前需要共同落定的契约（未实现的建议，不冒充已有API）

1. 发布配置从哪里读、放到运行时哪个字段、怎样标明版本。沿用已有版本机制，不让Agent直接读正在编辑的草稿。明确新发布版本对新会话/进行中会话的生效规则，不擅自覆盖现有会话版本固定机制。
2. 盘点现有审批、转人工能力的真实函数/接口/工具名称，确认V2运行时能调用。已有旧流程不等于当前V2一定有对应工具；若未暴露，应接既有业务服务，不重做审批系统。
3. 动作请求应能对应代表、会话、规则ID、请求摘要、所需业务参数和幂等标识；身份权限由服务端会话决定，不信任模型自填ownerId。
4. 返回需区分created、already_pending、needs_information、forbidden、failed等含义（名称可适配现有返回）。必须携带可追查的真实记录编号，失败不返回虚假成功。
5. 多条边界冲突时优先级沿用已有规则；没有既定规则则在实现前共同确定并写入测试，不依赖模型随机选。

### 分步骤联调

A. 识别测试：先用固定规则与对话判断命中的规则ID及动作。价格咨询不审批、申请折扣需审批、明确找本人按handoff处理、自定义禁止事项decline、普通咨询正常回答。

B. 真业务调用：在测试环境发起请求，检查后台确实生成了正确代表/会话的审批或接待记录。连续点击或网络重试不能重复创建同一请求。

C. 异常测试：缺参数、无人工权益、后台失败、审批拒绝、等待中；Agent只能描述真实状态。前端显示与后台记录一致。

D. 发布联调：未发布的修改不影响当前正式规则；发布后按双方约定的版本生效规则使用新配置；另一代表的数据不能混入。

E. 结果闭环：若现有审批流程有回传，则验证批准/拒绝/等待后的会话回复；缺少的环节单独列缺口，不能仅凭“调用创建成功”宣称整条流程完成。

同事交付：规则输入/实际工具调用约定、识别与业务回执示例、测试记录、依赖我们补的接口清单及错误码；我们负责配置发布、页面、业务记录和完整联调。
